# 0005 明确不做清单

状态：生效

以下能力经评估后明确不做，重新提出需要先推翻本条：

- 写入租约（MasteryPathLease）：单进程 + `DB_LOCK` 串行化写，没有并发写竞争。
- 跨端回放种子：没有多端同步场景，FSRS 参数版本化已满足审计。
- 独立 `mistakes` 表：错题就是 `problems`，不重复建模。
- 锁定拖延 App / 系统级干预：违反工作区隔离红线。
- 多租户、商业化、订阅：与个人学习终端定位冲突。
- **插件 / MCP 机制骨架**（原 `plugins.py` + `GET /api/plugins`）：动态加载本地
  `plugin.py`（`spec.loader.exec_module`）等于给单机应用开一个任意代码执行口，
  而 `plugins/` 目录从未存在、端点恒返回空、无 UI 消费方。「以后可能有人写插件」
  不算场景。真要做时应当是显式开关 + 签名校验，而不是默认扫描加载。
- **学科渲染配置 API**（原 `render_config.py` + `/api/render-config(s)`）：前端渲染
  用写死的样式，三个路由零调用；它提供的学科显示名/图标与 `list_subjects()`
  构成双份事实来源，两者漂移时无人会发现。需要时按 `settings` 表加 20 行重建，
  但要先解决「谁是学科元数据的唯一来源」。
- **动态 PWA 清单**（原 `GET /api/pwa/manifest`）：`index.html` 直接引用静态
  `static/manifest.json`，该端点读的是同一份文件（`manifest.webmanifest` 从未存在，
  分支恒不命中），只是换了 Content-Type。同一份清单有两个出口必然漂移。

以上三条于本轮功能裁剪中删除（187 行 + 4 个路由），删除前均有实现、无消费方；
git 历史保留重建材料，但重建需先推翻本条并说明消费者是谁。

## 新功能准入
加功能前先回答：它强化了「尝试 → 提示 → 回忆 → 复习 → 口试」闭环里的哪一步？答不上来就不做。新字段或命令需要有真实使用场景，「将来可能需要」不算。
**反向同样成立**：新路由必须有消费者（前端调用点、CLI 或测试），否则不许注册 ——
「预留接口」在单人项目里等于无主代码，腐烂速度远快于它将来被用上的概率。
